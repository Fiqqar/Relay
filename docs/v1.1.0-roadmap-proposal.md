# Relay v1.1.0 — Product Roadmap & Feature Proposal

> **Tanggal Penyusunan:** 3 September 2026  
> **Target Rilis:** Relay v1.1.0 (Minor Release — Backward Compatible, Zero Runtime Dependencies)  
> **Status:** Proposal / Review  

---

## 1. Filosofi Desain & Non-Goals Acuan

Proposal ini dirancang berlandaskan prinsip arsitektur dan batasan produk yang telah didefinisikan sejak awal pengembangan Relay (`docs/SPEC.md`, `docs/ADR.md`, `docs/ROADMAP.md`):

1. **Zero Runtime Dependencies (ADR-001):**  
   Codebase tetap 100% Python Standard Library (`dependencies = []`). Tidak ada penambahan pustaka pihak ketiga seperti `requests`, `typer`, `pydantic`, atau `textual`.
2. **Subprocess Git Tanpa Library (ADR-002):**  
   Eksekusi Git murni menggunakan `subprocess.run(..., shell=False)` dengan argumen bertipe list (`argv-as-list`). Keamanan terhadap *Git option injection* tetap menjadi prioritas mutlak.
3. **Manual Fallback Guarantee (ADR-004 / G3):**  
   Relay tidak boleh memblokir alur kerja developer saat AI mati, timeout, rate-limited, atau offline.
4. **Performance & Sub-500ms CLI Overhead (NFR-1):**  
   Startup CLI dan eksekusi lokal harus tetap instan (< 50 ms overhead di luar latensi jaringan AI/remote).
5. **Non-Goals Tetap Dihormati (PRD §3):**  
   - *No Full-screen GUI/TUI*: Interaktivitas tetap berada pada prompt terminal standar.
   - *No Multi-Provider Cascading Failover*: Satu provider aktif + fallback manual yang dapat diprediksi.
   - *No Complex CI/CD / Release Orchestration*: Relay adalah Git automation tool untuk developer lokal, bukan engine CI atau release publisher.

## 2. Eksplorasi & Usulan Fitur per Area

---

### AREA 1: WORKFLOW & PRODUKTIVITAS

#### Fitur 1.1: Direct Commit Message Flag (`-m` / `--message`) pada Root CLI
- **Kategori:** Workflow & Produktivitas
- **Masalah yang Diselesaikan:**  
  Saat ini, perintah utama `relay --solo` atau `relay --team` selalu memanggil LLM (atau menunggu fallback jika API key kosong/error). Developer yang sudah tahu persis pesan commit yang ingin ditulis (misal hotfix 1 baris, commit typo, atau skrip otomatisasi) terpaksa harus menunggu respons AI lalu menolaknya, atau keluar dari Relay dan mengetik `git commit -m ... && git push`. `relay squash` sudah memiliki flag `-m`, tetapi root CLI belum.
- **Cara Kerja yang Diusulkan:**  
  Menambahkan argumen `-m` / `--message` pada root CLI parser:
  ```bash
  relay -m "fix(auth): correct token expiry check" --yes
  relay --team "login" -m "feat(auth): add google oauth provider"
  ```
  Jika `-m` diberikan, Relay melewati tahap pemanggilan AI, memvalidasi format Conventional Commit pesan tersebut (atau meminta konfirmasi jika tidak valid), langsung membuat commit dan melakukan push.
- **Dampak ke User:**  
  **Sana (Solo Dev)** dan **Marcus (Team Dev)**: Menghilangkan friksi untuk commit cepat tanpa kehilangan otomasi staging dan push.
- **Kompleksitas Implementasi:** **Small**  
  *File yang disentuh:* `relay/cli.py` (tambah argument), `relay/orchestrator.py` (bypass AI generate jika message diberikan).
- **Risiko / Trade-off:**  
  Rendah. Format Conventional Commit tetap divalidasi oleh `relay/commit.py:validate_conventional()`.
- **Prioritas:** **Must-have (v1.1.0 Core)**

---

#### Fitur 1.2: Multi-Commit Soft Undo (`relay undo --count N`)
- **Kategori:** Workflow & Produktivitas
- **Masalah yang Diselesaikan:**  
  Saat ini `relay undo` melakukan `git reset --soft HEAD~1` secara kaku (tepat 1 commit). Jika developer membuat 2 atau 3 commit lokal berturut-turut dan ingin menggabungkannya kembali ke staging area untuk dirapikan, mereka harus mengetik `relay undo` berulang kali.
- **Cara Kerja yang Diusulkan:**  
  Menambahkan opsi flag numerik `-n` / `--count` pada subcommand `undo`:
  ```bash
  relay undo -n 3
  relay undo 2
  ```
  Relay memvalidasi bahwa `commit_count() > count`, lalu menjalankan `git reset --soft HEAD~{count}` dengan aman (menggunakan guard integer dan validasi `not target.startswith("-")`).
- **Dampak ke User:**  
  **Sana (Solo Dev)**: Mempermudah eksperimen lokal dan perbaikan commit bertahap sebelum di-push.
- **Kompleksitas Implementasi:** **Small**  
  *File yang disentuh:* `relay/cli.py`, `relay/undo.py`, `tests/test_undo.py`.
- **Risiko / Trade-off:**  
  Perlu memastikan pesan peringatan jika commit yang di-undo sudah terlanjur di-push ke remote.
- **Prioritas:** **Nice-to-have**

---

#### Fitur 1.3: Subdirectory / Path-Scoped Staging (`--dir` / `--only`)
- **Kategori:** Workflow & Produktivitas
- **Masalah yang Diselesaikan:**  
  Di dalam monorepo atau workspace multi-package (misal root repo memiliki `packages/api` dan `packages/web`), `relay --solo` menjalankan `git add .` dari current working directory, namun seringkali developer sedang bekerja di subfolder tertentu dan hanya ingin men-stage perubahan di modul tersebut tanpa menyentuh modul tetangga.
- **Cara Kerja yang Diusulkan:**  
  Menambahkan flag `--only <path>` (repeatable) atau `--dir <path>`:
  ```bash
  relay --only packages/api --yes
  relay --only src/auth/ --team "auth-refactor"
  ```
  Relay menjalankan `git add -- <paths>` alih-alih `git add .`, dan membatasi diff yang dikirim ke LLM hanya pada path tersebut.
- **Dampak ke User:**  
  **Marcus (Team Dev in Monorepo)**: Mengisolasi commit per-package tanpa perlu staging manual lewat `git add`.
- **Kompleksitas Implementasi:** **Medium**  
  *File yang disentuh:* `relay/cli.py`, `relay/orchestrator.py`, `tests/test_orchestrator.py`.
- **Risiko / Trade-off:**  
  Harus memastikan path divalidasi agar tidak berawalan `-` untuk mencegah Git option injection.
- **Prioritas:** **Nice-to-have**

### AREA 2: AI & COMMIT MESSAGE QUALITY

#### Fitur 2.1: Context-Aware Commit Generation via Recent History (`recent_commits` prompt injection)
- **Kategori:** AI & Commit Message Quality
- **Masalah yang Diselesaikan:**  
  Saat ini prompt yang dikirim ke LLM hanya memuat `diff`, `stat`, dan nama branch. LLM tidak memiliki konteks mengenai gaya penulisan scope repositori tersebut (misal apakah tim menggunakan `feat(core):` atau `feat(backend):`), sehingga scope yang dihasilkan sering acak atau tidak konsisten dengan riwayat commit sebelumnya.
- **Cara Kerja yang Diusulkan:**  
  Di `relay/orchestrator.py`, ambil 3–5 commit terakhir dari branch saat ini (`git log -5 --format="%s"` via `git.recent_subjects(5)`). Masukkan ke dalam prompt di `relay/ai/base.py:build_prompt`:
  ```text
  Recent commits in this branch:
  - feat(auth): add jwt middleware
  - test(auth): unit tests for jwt token validation
  - fix(auth): handle expired token gracefully
  ```
  LLM akan secara otomatis menangkap pola scope `(auth)` dan gaya bahasa imperatif yang konsisten dengan riwayat tim.
- **Dampak ke User:**  
  **Marcus (Team Dev)** & **Sana (Solo Dev)**: Kualitas commit message dan akurasi pemilihan scope meningkat drastis tanpa perlu instruksi manual.
- **Kompleksitas Implementasi:** **Small**  
  *File yang disentuh:* `relay/git_manager.py`, `relay/ai/base.py`, `relay/orchestrator.py`, `tests/test_ai.py`.
- **Risiko / Trade-off:**  
  Menambah sedikit token prompt (~50 token), namun masih jauh di bawah batas token budget (512 KiB).
- **Prioritas:** **Must-have (v1.1.0 Core)**

---

#### Fitur 2.2: Configurable Scopes & Custom AI Guidelines (`[commit.scopes]` & `[ai.prompt]`)
- **Kategori:** AI & Commit Message Quality
- **Masalah yang Diselesaikan:**  
  Setiap tim engineering biasanya memiliki aturan internal (misal: "hanya gunakan scope `api`, `web`, `core`, `db`", atau "jangan gunakan scope jika perubahan menyentuh >3 modul"). Saat ini `SYSTEM_PROMPT` di Relay bersifat statis dan tidak dapat dipengaruhi oleh konfigurasi repositori.
- **Cara Kerja yang Diusulkan:**  
  Menambahkan dukungan tabel konfigurasi di `config.toml`:
  ```toml
  [commit]
  scopes = ["api", "web", "core", "db", "infra"]
  
  [ai.prompt]
  extra_instructions = "Scope must reflect the primary package modified."
  ```
  `build_prompt` akan menyematkan daftar scope yang diperbolehkan dan instruksi tambahan tersebut ke dalam prompt sistem.
- **Dampak ke User:**  
  **Marcus (Team Dev)**: Menjamin kepatuhan standar commit tim tanpa harus sering memilih opsi `[Edit]` di prompt konfirmasi.
- **Kompleksitas Implementasi:** **Medium**  
  *File yang disentuh:* `relay/config.py`, `relay/ai/base.py`, `tests/test_config.py`, `tests/test_ai.py`.
- **Risiko / Trade-off:**  
  Validasi parsing TOML harus toleran jika tipe data salah (sesuai aturan `docs/WORKING_RULES.md`).
- **Prioritas:** **Nice-to-have**

---

#### Fitur 2.3: Re-prompt Variance pada Menu Retry (`[r] Retry`)
- **Kategori:** AI & Commit Message Quality
- **Masalah yang Diselesaikan:**  
  Ketika user menolak usulan pesan commit pertama dan memilih `r` (Retry), Relay memanggil ulang API dengan prompt yang 100% sama. Pada model dengan temperature rendah (seperti `0.2` pada Ollama/Gemini), model sering mengembalikan teks yang identik atau nyaris sama, membuat fitur retry terkesan "rusak".
- **Cara Kerja yang Diusulkan:**  
  Pada panggilan retry di `_prompt_ai_message`, tambahkan feedback singkat ke prompt:
  ```text
  Previous suggestion '{rejected_message}' was rejected by the developer. Propose a distinct, alternative Conventional Commit summary.
  ```
  Dengan demikian, percobaan kedua dijamin menyajikan perspektif atau sudut pandang fungsional yang berbeda.
- **Dampak ke User:**  
  Semua pengguna: Fitur retry menjadi bermakna dan berguna, tidak lagi membuang waktu dan biaya API untuk respons duplikat.
- **Kompleksitas Implementasi:** **Small**  
  *File yang disentuh:* `relay/orchestrator.py`, `relay/ai/base.py`, `tests/test_orchestrator.py`.
- **Risiko / Trade-off:**  
  Sangat kecil, tidak ada efek samping ke logika validasi.
- **Prioritas:** **Must-have (v1.1.0 Core)**

### AREA 3: FORGE INTEGRATION (GitHub/GitLab/Bitbucket)

#### Fitur 3.1: Self-Hosted GitHub Enterprise Support via `RELAY_TRUSTED_GITHUB_HOSTS`
- **Kategori:** Forge Integration
- **Masalah yang Diselesaikan:**  
  Relay sudah mendukung self-hosted GitLab via `RELAY_TRUSTED_GITLAB_HOSTS` / `trusted_gitlab_hosts`. Namun untuk GitHub, `pr.py` saat ini menolak host apapun selain `github.com` (`unsupported or untrusted forge host`). Organisasi enterprise yang menggunakan GitHub Enterprise Server (GHES, misal `github.mycompany.internal`) tidak dapat menggunakan `relay pr`.
- **Cara Kerja yang Diusulkan:**  
  Menambahkan env-only variable `RELAY_TRUSTED_GITHUB_HOSTS` (dan opsi config `[relay] trusted_github_hosts = [...]`), setara dengan implementasi GitLab:
  - Jika host origin cocok dengan trusted GitHub hosts, `GitHubClient` menggunakan base URL `https://{host}/api/v3` (standar REST API GHES).
  - Tetap dilindungi oleh SSRF and scheme validation yang ketat.
- **Dampak ke User:**  
  **Enterprise Developers**: Membuka adopsi Relay di lingkungan perusahaan dengan instance internal GitHub.
- **Kompleksitas Implementasi:** **Medium**  
  *File yang disentuh:* `relay/config.py`, `relay/github.py`, `relay/pr.py`, `tests/test_pr.py`, `tests/test_github.py`.
- **Risiko / Trade-off:**  
  Harus memastikan base URL GHES (`/api/v3`) diproses dengan benar tanpa bentrok dengan API `api.github.com` publik.
- **Prioritas:** **Must-have (Paritas Enterprise)**

---

#### Fitur 3.2: PR Body Template Discovery & Custom Description (`relay pr --body`)
- **Kategori:** Forge Integration
- **Masalah yang Diselesaikan:**  
  Saat ini `relay pr` selalu menyusun body PR berupa daftar bullet commit: `Commits in <head> (vs <base>): - ...`. Pengguna tidak bisa menentukan deskripsi PR sendiri, dan Relay tidak membaca file template PR standar (`.github/pull_request_template.md`).
- **Cara Kerja yang Diusulkan:**  
  1. Tambahkan flag `--body <text>` dan `--body-file <path>` pada subcommand `pr`.
  2. Jika flag tidak diberikan, Relay memeriksa apakah file `.github/pull_request_template.md` atau `PULL_REQUEST_TEMPLATE.md` ada di repositori. Jika ada, isi template tersebut digunakan sebagai dasar body PR dan daftar commit dilampirkan di bagian bawah.
- **Dampak ke User:**  
  **Marcus (Team Dev)**: Menghormati checklist PR tim tanpa perlu copas manual di browser.
- **Kompleksitas Implementasi:** **Medium**  
  *File yang disentuh:* `relay/cli.py`, `relay/pr.py`, `tests/test_pr.py`.
- **Risiko / Trade-off:**  
  Pembacaan file template harus dibatasi ukurannya (misal max 64 KiB) agar tidak membebani memori.
- **Prioritas:** **Nice-to-have**

---

#### Fitur 3.3: Assign Reviewers & Labels pada PR (`relay pr --reviewer` / `--label`)
- **Kategori:** Forge Integration
- **Masalah yang Diselesaikan:**  
  Setelah `relay pr` selesai membuka PR, developer tetap harus membuka tab browser hanya untuk menambahkan rekan tim sebagai reviewer dan menempelkan label PR (`bug`, `enhancement`).
- **Cara Kerja yang Diusulkan:**  
  Menambahkan flag `--reviewer` / `-r` dan `--label` / `-l` pada `relay pr`:
  ```bash
  relay pr --reviewer alice,bob --label backend,ready-for-review
  ```
  Setelah PR dibuat (atau saat update PR), client mengirimkan HTTP request kedua ke endpoint forge (`/requested_reviewers` dan `/labels` di GitHub; `assignee_ids` / `labels` di GitLab; `reviewers` di Bitbucket).
- **Dampak ke User:**  
  **Marcus (Team Dev)**: Alur pembuatan PR menjadi 100% tuntas di terminal.
- **Kompleksitas Implementasi:** **Medium**  
  *File yang disentuh:* `relay/cli.py`, `relay/pr.py`, `relay/github.py`, `relay/gitlab.py`, `relay/bitbucket.py`, unit tests masing-masing forge.
- **Risiko / Trade-off:**  
  Perlu penanganan error yang anggun (*graceful failure*): jika username reviewer salah ketik, PR utama tidak boleh gagal, melainkan menampilkan peringatan.
- **Prioritas:** **Nice-to-have**

### AREA 4: CONFIGURABILITY & TEAM ADOPTION

#### Fitur 4.1: Safe Repo-Local Configuration (`.relay.toml` di Root Repositori)
- **Kategori:** Configurability & Team Adoption
- **Masalah yang Diselesaikan:**  
  Saat ini Relay hanya memuat konfigurasi dari `$XDG_CONFIG_HOME/relay/config.toml` (user profile global). Setiap anggota tim baru harus menyalin konfigurasi manual ke mesin masing-masing. ADR-005 melarang repo-local config karena risiko keamanan (attacker repo bisa mengubah API base URL atau mengeksekusi hooks berbahaya).
- **Cara Kerja yang Diusulkan (Safe Boundary Model):**  
  Izinkan pemuatan file `.relay.toml` di root repositori Git, dengan **Strict Security Allowlist**:
  - *Key yang DIIZINKAN dari repo-local:*
    - `branch_template = "<type>/<feature>"`
    - `[team.protected] branches = ["main", "develop"]`
    - `[relay.ignore] paths = ["dist/*", "*.lock"]`
    - `[commit] scopes = ["api", "ui", "core"]`
    - `default_base_branch = "main"`
  - *Key yang DITOLAK / DIABAIKAN dengan Warning dari repo-local:*
    - Semua `*_base_url` (mencegah credential redirection)
    - Semua `[hooks]` (mencegah Arbitrary Code Execution)
    - Semua token / keys (tetap env-only)
- **Dampak ke User:**  
  **Marcus (Team Dev & Lead)**: Cukup commit satu file `.relay.toml` ke repo tim; seluruh tim otomatis mengikuti standar protected branches, branch naming, dan ignore paths yang sama secara aman.
- **Kompleksitas Implementasi:** **Medium**  
  *File yang disentuh:* `relay/config.py`, `tests/test_config.py`, `tests/test_security_audit.py`.
- **Risiko / Trade-off:**  
  Harus diuji ketat dengan security regression test untuk memastikan `hooks` dan `base_url` benar-benar diabaikan jika berasal dari repo-local.
- **Prioritas:** **Must-have (v1.1.0 Core — Game Changer untuk Adopsi Tim)**

---

#### Fitur 4.2: Pre-Commit Secret & Large Binary Guard (Safety Preflight)
- **Kategori:** Configurability & Team Adoption
- **Masalah yang Diselesaikan:**  
  Developer sering tidak sengaja men-stage file kredensial lokal (seperti `.env`, `.pem`, `id_rsa`, `service-account.json`) atau file binary besar (seperti `.mp4`, `.zip`, dataset 50MB) saat menjalankan `relay --solo` (`git add .`). Relay langsung men-commit dan mem-push file tersebut ke remote publik sebelum developer menyadarinya.
- **Cara Kerja yang Diusulkan:**  
  Preflight check ringan di `orchestrator.py` sebelum generate commit:
  - Pindai daftar file yang di-stage: jika ada nama file sensitif yang cocok dengan blacklist bawaan (`.env*`, `*.pem`, `*.key`, `id_rsa*`, `*credentials*.json`), Relay **menolak melanjutkan** commit dan memberi tahu user untuk unstage file tersebut.
  - Periksa file berukuran > 10 MB (dapat dikonfigurasi).
  - Sediakan flag escape hatch `--allow-secrets` jika user memang sengaja ingin commit file tersebut.
- **Dampak ke User:**  
  Semua pengguna (terutama Solo & Team Dev): Menyelamatkan developer dari insiden kebocoran API key ke GitHub publik.
- **Kompleksitas Implementasi:** **Small**  
  *File yang disentuh:* `relay/orchestrator.py`, `relay/stage.py`, `tests/test_orchestrator.py`.
- **Risiko / Trade-off:**  
  Hanya memeriksa nama file dan ukuran stat, tidak membaca isi file sehingga performa tetap < 5ms.
- **Prioritas:** **Nice-to-have**

### AREA 5: OBSERVABILITY & DEBUGGING

#### Fitur 5.1: Active Provider Health Probe & Latency di `relay doctor --probe`
- **Kategori:** Observability & Debugging
- **Masalah yang Diselesaikan:**  
  `relay doctor` saat ini hanya mengecek keberadaan environment variable (misal `GEMINI_API_KEY is set`). Jika API key salah ketik, kuota habis, atau server sedang down, `doctor` tetap melaporkan `PASS`. User baru mengetahui masalahnya ketika alur kerja commit sedang berjalan.
- **Cara Kerja yang Diusulkan:**  
  Menambahkan flag `--probe` / `-p` pada `relay doctor`:
  ```text
  $ relay doctor --probe
  [relay doctor] Relay 1.1.0 - gemini provider
    ...
    provider: gemini   PASS   Gemini API (response latency: 240ms, key valid)
    GitHub token       PASS   authenticated as @Fiqqar (scopes: repo)
  ```
  Relay mengirimkan request ping/token validasi minimal ke endpoint provider dan forge, lalu menampilkan status autentikasi nyata beserta latensinya.
- **Dampak ke User:**  
  **Priya (Low-connectivity)** & developer baru: Memvalidasi kesiapan lingkungan secara tuntas sebelum mulai coding.
- **Kompleksitas Implementasi:** **Small**  
  *File yang disentuh:* `relay/doctor.py`, `tests/test_doctor.py`.
- **Risiko / Trade-off:**  
  Flag ini opt-in (`--probe`), sehingga `relay doctor` default tetap 100% offline dan instan.
- **Prioritas:** **Must-have (v1.1.0 Core)**

---

#### Fitur 5.2: Structured Performance & Timing Tracing (`relay --verbose`)
- **Kategori:** Observability & Debugging
- **Masalah yang Diselesaikan:**  
  Saat ini flag `--verbose` hanya mencetak perintah git (`git diff ...`). Developer tidak bisa mengetahui komponen mana yang memakan waktu (apakah `git add`, jaringan AI provider, atau `git push`).
- **Cara Kerja yang Diusulkan:**  
  Ketika `--verbose` aktif, Relay mencatat timer internal (`time.perf_counter()`) dan mencetak ringkasan diagnostik di akhir proses:
  ```text
  [relay:perf] git preflight: 14ms | stage: 22ms | AI generate (gemini): 310ms | git commit: 25ms | git push: 420ms | total: 791ms
  ```
- **Dampak ke User:**  
  Pengguna dengan koneksi fluktuatif dapat langsung mengetahui apakah perlambatan disebabkan oleh jaringan internet atau operasi disk lokal.
- **Kompleksitas Implementasi:** **Small**  
  *File yang disentuh:* `relay/orchestrator.py`.
- **Risiko / Trade-off:**  
  Hanya aktif saat `--verbose`, nol overhead saat eksekusi normal.
- **Prioritas:** **Nice-to-have**

### AREA 6: RESOLUSI ITEM PENDING

#### Fitur 6.1: Editor Fallback & Explicit Multi-Paragraph Input (Resolusi Item #8)
- **Kategori:** Resolusi Item Pending
- **Masalah yang Diselesaikan:**  
  Hasil re-audit mengidentifikasi bahwa mode manual fallback saat ini menghentikan pembacaan baris begitu user menekan Enter pada baris kosong (`if not line.strip(): break`). Hal ini menyebabkan pengguna **mustahil menulis body commit message multi-paragraf** (yang menurut konvensi Git harus dipisahkan oleh satu baris kosong).
- **Cara Kerja yang Diusulkan (Solusi Hibrida):**  
  1. *Prompt Terminal*: Tetap mempertahankan perilaku cepat saat ini (baris kosong = selesai) untuk input singkat 1 paragraf, tetapi tambahkan opsi terminasi eksplisit: jika pengguna memasukkan baris berisi tanda titik tunggal (`.`) atau menekan `Ctrl+D` (EOF), input selesai. Hal ini memungkinkan pengguna memasukkan baris kosong di tengah teks.
  2. *Editor Escape Hatch*: Pada prompt manual atau prompt konfirmasi `[Accept] [Edit] [Retry] [Abort]`, jika user memilih opsi `e` (Edit) dan terminal mendukung interaktivitas (TTY), Relay membuka text editor default pengguna (`$GIT_EDITOR` > `$EDITOR` > `nano`/`notepad`) dengan draf pesan commit. Setelah editor ditutup dan disimpan, commit dilanjutkan.
- **Dampak ke User:**  
  Semua pengguna: Menyelesaikan keterbatasan fungsionalitas mode manual tanpa merusak alur input cepat satu baris.
- **Kompleksitas Implementasi:** **Small**  
  *File yang disentuh:* `relay/orchestrator.py`, `tests/test_orchestrator.py`.
- **Risiko / Trade-off:**  
  Pemanggilan editor harus menggunakan `shell=False` dengan argv yang di-parse via `shlex.split()`, dan fallback kembali ke terminal jika editor gagal dibuka.
- **Prioritas:** **Must-have (v1.1.0 Core)**

## 3. Fitur yang Dianjurkan untuk DITOLAK / DITUNDA

| Fitur yang Diusulkan | Alasan Penolakan / Penundaan | Kaitan Filosofi / Dokumen |
|---|---|---|
| **Full-Screen Interactive TUI** (misal dengan `textual` / `curses`) | **DITOLAK**. Mengharuskan instalasi dependensi pihak ketiga, memperlambat startup CLI (>150ms), dan rawan rusak di berbagai emulator terminal Windows/PowerShell. | Melanggar ADR-001 (Zero runtime deps) & PRD §3 (Non-Goal G1/GUI). |
| **Multi-Provider Automatic Cascading Failover** (Gemini $\to$ OpenAI $\to$ Ollama) | **DITOLAK**. Membuat model mental tidak dapat diprediksi (commit dibuat oleh model yang mana?), melipatgandakan waktu tunggu saat offline (bisa timeout 30s + 30s = 60 detik sebelum fallback manual), dan memperumit konfigurasi. | Melanggar PRD §3 (Non-Goal: "No multi-provider failover; one configured provider + manual fallback") & ADR-013. |
| **Automated Semantic Versioning & Release Tagging (`relay release`)** | **DITUNDA**. Relay dirancang sebagai asisten alur kerja Git lokal harian, bukan pengganti tooling release management seperti *Release-Please* atau *Semantic-Release*. | Melanggar PRD §3 (Non-Goal: "No CI/CD pipeline orchestration"). |
| **Interactive Git Merge Conflict Resolver** | **DITOLAK**. Git bawaan dan editor modern (VSCode, JetBrains) sudah memiliki antarmuka penyelesaian konflik yang matang. Membangun merge conflict resolver di terminal menambah kompleksitas masif yang tidak relevan dengan tujuan inti Relay. | Fokus produk: Staging $\to$ Commit $\to$ Push $\to$ PR. |
